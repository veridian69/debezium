# Findings: Debezium Server plumbing proof

Date: 2026-10-09. Author: Spike. Status: verified against running containers on WSL Docker CE 29.8.2 / Compose v5.6.0.

Goal and acceptance: [debezium-plumbing-goal.md](debezium-plumbing-goal.md). Decisions and evidence trail: [work/2026-10-09-debezium-plumbing-proof.md](work/2026-10-09-debezium-plumbing-proof.md).

## Summary

The time-critical path works end to end: PostgreSQL logical replication through Debezium Server's native HTTP sink into a Java receiver, one complete envelope per POST, with the bulk schema left untouched. All eight acceptance checks pass in a single consolidated run (`runs/verify-20261009T184304Z.json`).

Two findings change how an Integration Broker endpoint would have to be built, and one changes how operations would have to watch Debezium. They are in the next section.

## Findings that matter for the production design

### 1. Retry exhaustion does not stop the container

Configured: HTTP sink timeout 5000 ms, 10 retries, 3000 ms interval.

Observed after stopping the receiver:

```
Failed to send event: HTTP connect timed out        (attempt 1)
Failed to send event: null                          (attempts 2..11, ~3 s apart)
ERROR [AsyncEmbeddedEngine] Engine has failed with : ... DebeziumException: Error while executing batch
Caused by: io.debezium.DebeziumException: Exceeded maximum number of attempts to publish event
Engine state has changed from 'POLLING_TASKS' to 'STOPPING' ... 'STOPPED'
[io.smallrye.health] Reporting health down status: {"status":"DOWN", ...}
```

- Budget exhausted after 39 to 48 s depending on how many attempts hit the connect timeout.
- The embedded engine stops. The Quarkus process keeps running. The container state stays `running`, exit code never set.
- `GET /q/health` returns HTTP 503 with `"status":"DOWN"`. Compose marks the container `unhealthy`.
- Nothing restarts it. With `restart: "no"` this is deliberate here; with `restart: unless-stopped` it would still not restart, because the process has not exited.

Recovery: `docker compose restart debezium` (`make recover`). Debezium resumed from the file offset and delivered the whole backlog (14 events in the manual test, 7 in each verified run) with zero duplicates.

Consequence for production: monitoring must watch the health endpoint or the Compose/Kubernetes health status, not process liveness. On Kubernetes a liveness probe on `/q/health/live` would restart the pod automatically. Sink retries are finite and short; anything longer than roughly 30 s of receiver outage needs an external restart.

### 2. The HTTP sink sends no key and no destination in headers

Observed headers on every POST (`logs/receipts.jsonl`):

| Header | Value |
|---|---|
| `content-type` | `application/json` |
| `user-agent` | `Java-http-client/21.0.12.1` |
| `upgrade`, `http2-settings`, `connection` | h2c upgrade offer from the JDK client |
| `traceparent` | W3C trace context |
| `x-debezium-__debezium.context.connectorlogicalname` | base64 of `{"schema":{"type":"string","optional":false},"payload":"plumbing"}` |
| `x-debezium-__debezium.context.connectorname` | base64, payload `postgresql` |
| `x-debezium-__debezium.context.runid` | base64, payload is a UUID per Debezium start |
| `x-debezium-__debezium.context.taskid` | base64, payload `0` |

There is no header for the record key and none for the destination topic (`plumbing.timecritical.orders`). The receiver must derive table and key from the body: `source.schema`, `source.table`, `after.id` or `before.id`.

Consequence: an Integration Broker handler cannot route on headers. It parses the envelope first. If routing by table before parsing is wanted, a separate sink URL per table is not available either; the sink has one URL.

### 3. Envelope shape with schema metadata disabled

`debezium.format.value.schemas.enable=false` gives the bare payload, which is what the receiver logs:

```json
{"before":null,
 "after":{"id":1,"external_ref":"cust-seed-1","name":"Ada Lovelace","email":"ada@example.test","created_at":"2026-10-09T18:24:31.024549Z"},
 "source":{"version":"3.7.0.Final","connector":"postgresql","name":"plumbing","ts_ms":1791570312134,"snapshot":"first","db":"appdb","sequence":"[null,\"29593976\"]","ts_us":1791570312134792,"ts_ns":1791570312134792000,"schema":"timecritical","table":"customers","txId":781,"lsn":29593976,"xmin":null,"origin":null,"origin_lsn":null},
 "transaction":null,"op":"r","ts_ms":1791570312193,"ts_us":1791570312193972,"ts_ns":1791570312193972382}
```

- `op` is `r` for snapshot, `c`, `u`, `d` for live changes.
- `source.snapshot` is not just `true`/`false`. Values seen: `first`, `true`, `last_in_data_collection`, `first_in_data_collection`, `last`, `false`. Anything matching on `"true"` alone will miss snapshot rows.
- `before` is fully populated on `u` and `d` only because the captured tables have `REPLICA IDENTITY FULL`. With the default identity, `before` would hold the primary key only.
- `timestamptz` arrives as an ISO-8601 string. Integer cents were used for money to avoid Debezium's decimal encoding; a production schema with `numeric` columns needs `decimal.handling.mode` decided explicitly.
- Tombstones are disabled at the source. The receiver additionally accepts an empty body as a tombstone (204, receipt only) so the proof does not depend on that single property.

### 4. Delivery characteristics

- One POST per row change. A transaction touching four rows produced four envelopes with the same `source.txId`.
- Ordering within the stream was preserved in every run.
- Measured delivery time from commit (`source.ts_ms`) to receipt: roughly 450 to 800 ms across runs, about 600 ms in the final run. Local observation on WSL, not a benchmark.
- No duplicates were observed in any run, including recovery after the long outage and after a full stack restart. Delivery is still at-least-once; a restart between a successful POST and the offset flush would replay. The receiver keeps duplicates and the verifier identifies them by `(source.lsn, schema, table, op, key)`.

### 5. Bulk strand isolation

The `bulk` schema is excluded by `schema.include.list` and `table.include.list`, and the publication lists only the three captured tables. Bulk inserts and updates in the same database produced no envelopes. The verifier proves this by ordering: it makes a bulk change, then a time-critical change, and asserts the time-critical event arrived with no bulk event before it.

## Flow

```mermaid
sequenceDiagram
    participant G as generator (psql)
    participant P as PostgreSQL 18.6
    participant D as Debezium Server 3.7
    participant R as Java receiver
    participant L as logs/events.jsonl
    G->>P: BEGIN; 4 inserts; COMMIT
    P-->>D: pgoutput via slot dbz_slot
    loop one POST per row
        D->>R: POST /events (envelope)
        R->>L: append + fsync
        R-->>D: 200
    end
    Note over D,R: receiver down > ~40 s: engine stops, /q/health 503, container keeps running
    R-->>D: (after `make recover`) backlog delivered from stored offset
```

## Process notes

- Four Codex workers built the units in parallel from Lead-fixed contracts; one repair round was needed.
- Two defects were in the contracts, not the workers: the snapshot value set and the assumption that Debezium exits on retry exhaustion. Both are now documented from evidence rather than from the documentation.
- Receiver unit tests: 6 run, 0 failures, executed inside the Maven build stage and once more explicitly.

## Deferred

- Dedicated replication role instead of the superuser, to mirror production grants.
- Receiver failure-injection endpoint to exercise 5xx retries without stopping the container.
- Kubernetes liveness probe on `/q/health/live` as the production answer to finding 1.
